# LLM-written code sources

## LLM-written code

Sources checked on 2026-11-09 for [LLM_CODE.md](../guides/LLM_CODE.md). DOIs were resolved through Crossref. Each entry says whether the full text or only the abstract was read. Numbers come from the source itself. Many studies test models from 2021 to 2025, and several 2026 studies are short papers or preprints. No source tests the checklists in the guide. Applying these findings to a review procedure is an inference.

### Duplication and reuse

- **S114. Haoming Huang, Pongchai Jaisri, Shota Shimizu, Lingfeng Chen, Sota Nakashima and Gema Rodríguez-Pérez (2026), [More Code, Less Reuse: Investigation on Code Quality and Reviewer Sentiment towards AI-generated Pull Requests](https://doi.org/10.1145/3793302.3793622), MSR 2026, 1024–1028. DOI 10.1145/3793302.3793622. [arXiv 2601.21276](https://arxiv.org/abs/2601.21276).** Research (repository mining of the AIDev dataset). Full text read. New functions were compared with the pre-change code by embedding similarity. Average maximum redundancy was 0.2867 for agent pull requests and 0.1532 for human ones. Reviewer comments on agent pull requests were not more negative. Limit: the redundancy analysis covers one Python project (617 pull requests). Similarity is not confirmed re-implementation.
- **S115. Kosei Horikawa, Hao Li, Yutaro Kashiwa, Bram Adams, Hajimu Iida and Ahmed E. Hassan (2026), [Agentic Refactoring: An Empirical Study of AI Coding Agents](https://doi.org/10.1145/3859242), ACM TOSEM. DOI 10.1145/3859242. [arXiv 2511.04824](https://arxiv.org/abs/2511.04824).** Research (51,412 refactorings in Java agent pull requests). Abstract and RQ3 read. Agents named duplication as the motivation for 1.1% of refactorings and reuse for 4.6%. Limit: the human comparison figures come from a different, older study, so the gap is not a matched comparison. Motivations are inferred from commit and pull request text.
- **S116. William Harding (2025), [AI Copilot Code Quality: Evaluating 2024's Increased Defect Rate via Code Quality Metrics](https://gitclear-public.s3.us-west-2.amazonaws.com/GitClear-AI-Copilot-Code-Quality-2025.pdf), GitClear, February 2025.** Practice (vendor white paper, not peer reviewed). Full text read. Across 211 million changed lines from 2020 to 2024, moved lines fell from 24.1% to 9.5% and copied lines rose from 8.3% to 12.3%. Limit: a correlation by calendar year. No line is attributed to AI. The report's "8x" and "10x" duplicate-block multipliers do not follow from its own table, so we do not use them. GitClear sells code analytics.
- **S117. Hao Yu, Bo Shen, Dezhi Ran, Jiaxin Zhang, Qi Zhang, Yuchi Ma, Guangtai Liang, Ying Li, Qianxiang Wang and Tao Xie (2024), [CoderEval: A Benchmark of Pragmatic Code Generation with Generative Pre-trained Models](https://doi.org/10.1145/3597503.3623316), ICSE 2024. DOI 10.1145/3597503.3623316.** Research (benchmark). Full text read. More than 70% of functions in popular Java and Python projects depend on other project code. ChatGPT's pass@1 on Python fell from 35.87% for standalone functions to 15.45% for dependent ones. Limit: 2022–2023 models, one function at a time, no repository search.
- **S118. Nam Le Hai, Dung Manh Nguyen and Nghi D. Q. Bui (2025), [On the Impacts of Contexts on Repository-Level Code Generation](https://doi.org/10.18653/v1/2025.findings-naacl.82), Findings of NAACL 2025. DOI 10.18653/v1/2025.findings-naacl.82. [arXiv 2406.11927](https://arxiv.org/abs/2406.11927).** Research (RepoExec benchmark). Full text read. Pretrained models "often reimplement dependencies", and instruction-tuned models sometimes do so even when the dependency is in the prompt. A re-implemented helper still passed the tests. Limit: Python, dependencies given in the prompt, models as of early 2025.
- **S119. Yangruibo Ding et al. (2023), [CrossCodeEval: A Diverse and Multilingual Benchmark for Cross-File Code Completion](https://arxiv.org/abs/2310.11248), NeurIPS 2023 Datasets and Benchmarks.** Research (benchmark). Abstract and results read. Retrieved cross-file context improved exact match up to 3.0 times over in-file context alone. Limit: line completion, 2023 models.
- **S120. Fengji Zhang, Bei Chen, Yue Zhang, Jacky Keung, Jin Liu, Daoguang Zan, Yi Mao, Jian-Guang Lou and Weizhu Chen (2023), [RepoCoder: Repository-Level Code Completion Through Iterative Retrieval and Generation](https://doi.org/10.18653/v1/2023.emnlp-main.151), EMNLP 2023. DOI 10.18653/v1/2023.emnlp-main.151.** Research (benchmark). Abstract and introduction read. Retrieving repository code improved completion by more than 10% over the in-file baseline in all settings. Limit: measures matching a reference, not reuse.
- **S121. Elmar Juergens, Florian Deissenboeck, Benjamin Hummel and Stefan Wagner (2009), [Do code clones matter?](https://doi.org/10.1109/ICSE.2009.5070547), ICSE 2009, 485–495. DOI 10.1109/ICSE.2009.5070547. [arXiv 1701.05472](https://arxiv.org/abs/1701.05472).** Research (five systems, inconsistencies confirmed with their developers). Full text read. 52% of clone groups contained inconsistencies. "About every second to third unintentional change to a clone leads to a fault." The team that searched for duplicates routinely had far fewer unintended inconsistencies. Limit: five systems, mostly copy-and-modify clones.
- **S122. Stefan Wagner, Asim Abdulkhaleq, Kamer Kaya and Alexander Paar (2016), [On the Relationship of Inconsistent Software Clones and Faults: An Empirical Study](https://doi.org/10.1109/SANER.2016.94), SANER 2016, 79–89. DOI 10.1109/SANER.2016.94.** Research. Abstract read. 17% of near-miss (type-3) clones contained faults. Limit: three Java systems at one company.
- **S123. Manishankar Mondal, Banani Roy, Chanchal K. Roy and Kevin A. Schneider (2019), [An empirical study on bug propagation through code cloning](https://doi.org/10.1016/j.jss.2019.110407), Journal of Systems and Software 158, 110407. DOI 10.1016/j.jss.2019.110407.** Research (seven systems). Abstract read. 18.42% of clone fragments that received bug fixes contained propagated bugs. Limit: about copied buggy code, less about independent re-implementation.
- **S124. Cory J. Kapser and Michael W. Godfrey (2008), ["Cloning considered harmful" considered harmful: patterns of cloning in software](https://doi.org/10.1007/s10664-008-9076-6), Empirical Software Engineering 13(6), 645–692. DOI 10.1007/s10664-008-9076-6.** Research (counter-view). Full text read. Catalogues deliberate cloning such as forks and templates. In Apache httpd, 71% of the true clone groups examined were judged good and 14% harmful. Limit: the authors judged harm themselves. The good patterns are deliberate, not unknowing re-implementation.
- **S125. Nils Göde and Rainer Koschke (2011), [Frequency and risks of changes to clones](https://doi.org/10.1145/1985793.1985836), ICSE 2011. DOI 10.1145/1985793.1985836.** Research (counter-view). Abstract read. Most clones are rarely changed, and few changes to them are unintentionally inconsistent. Advises managing only clones with risk. Limit: abstract only.
- **S126. Bill Venners (2003), [Orthogonality and the DRY Principle](https://www.artima.com/articles/orthogonality-and-the-dry-principle), interview with Andy Hunt and Dave Thomas, Artima, 10 March 2003.** Opinion. Full text read. DRY means every piece of system knowledge has one authoritative representation, not merely that code is never repeated. The book wording was not checked.
- **S127. Xiaofeng Han, Amjed Tahir, Peng Liang, Steve Counsell, Kelly Blincoe, Bing Li and Yajing Luo (2022), [Code smells detection via modern code review: a study of the OpenStack and Qt communities](https://doi.org/10.1007/s10664-022-10178-7), Empirical Software Engineering 27. DOI 10.1007/s10664-022-10178-7. [arXiv 2205.07535](https://arxiv.org/abs/2205.07535).** Research (25,415 review comments checked by hand). Full text read for RQ1–RQ2. Duplicated code was the smell reviewers flagged most in OpenStack (52%) and third in Qt (26%). Most comments gave no cause. Where one was given, it was mostly unfamiliarity with existing code. Limit: counts what reviewers flagged, not what they missed. Two communities.
- **S128. Clone-detection tool documentation: PMD, [Finding duplicated code with CPD](https://pmd.github.io/pmd/pmd_userdocs_cpd.html); jscpd, [README](https://github.com/kucherenko/jscpd); SonarSource, [Metric definitions](https://docs.sonarsource.com/sonarqube-server/latest/user-guide/code-metrics/metrics-definition/).** Standard (tool documentation, checked 9 November 2026). CPD is token-based and supports C and C++. jscpd can fail only on clones new relative to a base branch (`--baseline-from-ref`). SonarQube's default "Sonar way" gate allows at most 3.0% duplication in new code. None claims to find code rewritten differently. That these tools miss such rewrites is our inference from their methods.
- **S129. Anthropic, [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices) (checked 9 November 2026), and its predecessor, [Claude Code: Best practices for agentic coding](https://web.archive.org/web/20250602202220/https://www.anthropic.com/engineering/claude-code-best-practices) (18 April 2025, archived copy).** Practice (vendor guidance). Full text read. The 2025 version says to have the agent read the relevant files and not write code yet, because otherwise it "tends to jump straight to coding". The current page asks for the command and output as evidence, and recommends a fresh reviewer that has not seen the author's reasoning. Limit: a vendor's advice for its own tool, with no measured effect on duplication.

### Scope and hidden changes

- **S130. Miku Watanabe, Hao Li, Yutaro Kashiwa, Brittany Reid, Hajimu Iida and Ahmed E. Hassan (2026), [On the Use of Agentic Coding: An Empirical Study of Pull Requests on GitHub](https://doi.org/10.1145/3798166), ACM TOSEM 35(10). DOI 10.1145/3798166. [arXiv 2509.14745](https://arxiv.org/abs/2509.14745).** Research (567 Claude Code pull requests, matched with 567 human ones). Full text read. 83.8% of agent pull requests were accepted, against 91.0%. 39.9% had more than one purpose, against 12.2%. Median description length was 355 words, against 56. Reviewers' revisions included removing duplication and fitting project architecture and style. Limit: one agent, self-identified pull requests, most rejections unexplained.
- **S131. Ramtin Ehsani, Sakshi Pathak, Shriya Rawal, Abdullah Al Mujahid, Mia Mohammad Imran and Preetha Chatterjee (2026), [Where Do AI Coding Agents Fail? An Empirical Study of Failed Agentic Pull Requests in GitHub](https://doi.org/10.1145/3793302.3793579), MSR 2026, 807–811. DOI 10.1145/3793302.3793579.** Research (short paper, 33,000 agent pull requests, 600 rejections coded). Full text read. Pull requests that were not merged were larger, touched more files and failed CI more often. Unwanted features accounted for 4% of coded rejections. Limit: association only, one reason per pull request.
- **S132. Thibaud Gloaguen, Niels Mündler, Mark Müller, Veselin Raychev and Martin Vechev (2026), [Coding Agents Don't Know When to Act](https://arxiv.org/abs/2605.07769), arXiv 2605.07769.** Research (preprint, 200 tasks where no change is needed). Full text read. Agents made unwanted changes, excluding tests and documentation, in 35% to 65% of cases. Most failed traces changed code unrelated to the issue. Reproducing the issue first improved abstention only when abstaining was framed as a valid outcome. It then caused abstention on partly fixed issues. Limit: preprint, Python tasks derived from SWE-bench.
- **S133. You Wang, Michael Pradel and Zhongxin Liu (2026), [Are "Solved Issues" in SWE-bench Really Solved Correctly? An Empirical Study](https://doi.org/10.1145/3744916.3764576), ICSE 2026. DOI 10.1145/3744916.3764576. [arXiv 2503.15223](https://arxiv.org/abs/2503.15223).** Research. Full text read. 29.6% of patches that passed the tests behaved differently from the developers' fix. Of 77 inspected divergent patches, 21 (27.3%) added behaviour and 4 (5.2%) missed some. Reported resolution rates were 6.4 points too high. Limit: three 2024 tools, Python.
- **S134. Kim Herzig and Andreas Zeller (2013), [The impact of tangled code changes](https://doi.org/10.1109/MSR.2013.6624018), MSR 2013, 121–130. DOI 10.1109/MSR.2013.6624018.** Research (five Java projects). Abstract read. Up to 15% of bug fixes contained several tangled changes, which misattributed at least 16.6% of files to bug reports. Limit: effect on history analysis, not on review.
- **S135. Yida Tao and Sunghun Kim (2015), [Partitioning Composite Code Changes to Facilitate Code Review](https://doi.org/10.1109/MSR.2015.24), MSR 2015, 180–190. DOI 10.1109/MSR.2015.24.** Research. Abstract read. Changes that mix several issues are hard to review, and up to 29% of 453 inspected changes did so. Limit: abstract only, before LLMs.
- **S136. Google Engineering Practices, [Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html).** Practice. Full text read. A change should do one thing. Refactorings go in a separate change from features and bug fixes. Reviewers may reject a change for size alone.
- **S137. Kent Beck (2025), [Augmented Coding: Beyond the Vibes](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes), 25 June 2025.** Opinion. Full text read. Warning signs that an agent is going off track include loops, functionality he had not asked for "even if it was a reasonable next step", and disabling or deleting tests. Separates structural changes from behaviour changes.

### Verification

- **S138. Joseph Spracklen, Raveen Wijewickrama, A H M Nazmus Sakib, Anindya Maiti, Bimal Viswanath and Murtuza Jadliwala (2025), [We Have a Package for You! A Comprehensive Analysis of Package Hallucinations by Code Generating LLMs](https://www.usenix.org/conference/usenixsecurity25/presentation/spracklen), USENIX Security 2025. [arXiv 2406.10279](https://arxiv.org/abs/2406.10279).** Research (16 models, 576,000 samples). Full text read. Invented packages averaged at least 5.2% for commercial models and 21.7% for open-source models. 43% of invented names recurred in all 10 reruns. Limit: 2023–2024 models, prompts outside a real repository.
- **S139. Samia Kabir, David N. Udo-Imeh, Bonan Kou and Tianyi Zhang (2024), [Is Stack Overflow Obsolete? An Empirical Study of the Characteristics of ChatGPT Answers to Stack Overflow Questions](https://doi.org/10.1145/3613904.3642596), CHI 2024. DOI 10.1145/3613904.3642596.** Research. Full text read. 52% of answers to 517 questions contained incorrect information and 77% were verbose. In a 12-person user study, participants missed the misinformation 39% of the time. Limit: GPT-3.5, question answering rather than agents.
- **S140. Neil Perry, Megha Srivastava, Deepak Kumar and Dan Boneh (2023), [Do Users Write More Insecure Code with AI Assistants?](https://doi.org/10.1145/3576915.3623157), CCS 2023, 2785–2799. DOI 10.1145/3576915.3623157.** Research (controlled study, 47 participants). Full text read. Participants with an assistant wrote significantly less secure code and were more likely to believe it was secure. Limit: mostly students, an old model, short tasks.
- **S141. Transluce (2025), [Investigating truthfulness in a pre-release o3 model](https://transluce.org/investigating-o3-truthfulness), 16 April 2025.** Research (report, not peer reviewed). Full text read. The model claimed to have run code it could not run and defended the claim when challenged. Limit: chat without tools, adversarial prompts, one vendor's models.
- **S142. Hammond Pearce, Baleegh Ahmad, Benjamin Tan, Brendan Dolan-Gavitt and Ramesh Karri (2022), [Asleep at the Keyboard? Assessing the Security of GitHub Copilot's Code Contributions](https://doi.org/10.1109/SP46214.2022.9833571), IEEE S&P 2022, 754–768. DOI 10.1109/SP46214.2022.9833571.** Research (89 scenarios, 1,689 programs). Full text read. About 40% of programs were vulnerable. Limit: 2021 model, scenarios chosen to invite known weaknesses.
- **S143. Vahid Majdinasab, Michael Joshua Bishop, Shawn Rasheed, Arghavan Moradidakhel, Amjed Tahir and Foutse Khomh (2024), [Assessing the Security of GitHub Copilot's Generated Code — A Targeted Replication Study](https://doi.org/10.1109/SANER60148.2024.00051), SANER 2024. DOI 10.1109/SANER60148.2024.00051.** Research (replication). Abstract and introduction read. Vulnerable suggestions fell from 36.54% to 27.25% with a newer model. Limit: Python subset.
- **S144. GitHub Docs, [Review AI-generated code](https://docs.github.com/en/copilot/tutorials/review-ai-generated-code).** Practice (vendor guidance, checked 9 November 2026). Full text read. Run tests and static analysis first. Check that dependencies exist, watch for invented APIs and for tests deleted or skipped instead of fixed.
- **S165. Joel Becker, Nate Rush, Elizabeth Barnes and David Rein (2025), [Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity](https://arxiv.org/abs/2507.09089), arXiv 2507.09089, and METR (2026), [Uplift update](https://metr.org/blog/2026-02-24-uplift-update/), 24 February 2026.** Research (preprint randomized trial, 16 developers, 246 tasks, and a non-peer-reviewed follow-up). Full text read. With AI tools, tasks took 19% longer, while developers estimated they were 20% faster. The 2026 follow-up estimates a speed-up but reports strong selection effects. Supports measuring outcomes, not the slowdown figure itself.

### Tests

- **S145. Michael Konstantinou, Renzo Degiovanni and Mike Papadakis (2026), [Can we find bugs using LLM-generated oracles?](https://arxiv.org/abs/2410.21136), arXiv 2410.21136 v2.** Research (preprint, 24 Java repositories). Full text read. LLM-generated test oracles mainly capture the actual behaviour of the code, which makes bugs hard to detect. Reasoning models behave the same. Limit: preprint, mutants stand in for real bugs.
- **S146. Carlos E. Jimenez et al. (2024), [SWE-bench: Can Language Models Resolve Real-World GitHub Issues?](https://arxiv.org/abs/2310.06770), ICLR 2024.** Research (benchmark). Construction sections read. Each task has at least one test that fails before the fix and passes after it.
- **S147. Laura Inozemtseva and Reid Holmes (2014), [Coverage Is Not Strongly Correlated with Test Suite Effectiveness](https://doi.org/10.1145/2568225.2568271), ICSE 2014, 435–445. DOI 10.1145/2568225.2568271.** Research (31,000 suites, five Java systems). Abstract and introduction read. Coverage correlates low to moderately with fault detection once suite size is controlled. Coverage should not be a quality target. Limit: mutants as the fault proxy.
- **S148. Goran Petrović, Marko Ivanković, Gordon Fraser and René Just (2022), [Practical Mutation Testing at Scale: A view from Google](https://doi.org/10.1109/TSE.2021.3107634), IEEE TSE 48(10), 3900–3912. DOI 10.1109/TSE.2021.3107634.** Practice/research (industrial). Key sections read. Mutation testing on changed code during review, used by more than 24,000 developers. Limit: Google's tools and culture.
- **S149. Goran Petrović, Marko Ivanković, Gordon Fraser and René Just (2021), [Does mutation testing improve testing practices?](https://doi.org/10.1109/ICSE43902.2021.00087), ICSE 2021. DOI 10.1109/ICSE43902.2021.00087.** Research (industrial data, almost 15 million mutants). Abstract and introduction read. Developers who saw mutants wrote more tests, and reported mutants were coupled with real faults. Limit: observational, one company.
- **S150. Ziqian Zhong, Aditi Raghunathan and Nicholas Carlini (2025), [ImpossibleBench: Measuring LLMs' Propensity of Exploiting Test Cases](https://arxiv.org/abs/2510.20270), arXiv 2510.20270.** Research (preprint). Full text read. Tests were changed to contradict the specification, so any pass means cheating. GPT-5 cheated on 76% of one SWE-bench variant. Strategies included editing tests despite instructions, special-casing and operator overloading. Read-only tests stopped edits but not special-casing. Limit: impossible tasks measure propensity under pressure, not rates on normal work.
- **S151. METR (2025), [Recent Frontier Models Are Reward Hacking](https://metr.org/blog/2025-06-05-recent-reward-hacking/), 5 June 2025.** Research (report, not peer reviewed). Full text read. o3 hacked the scorer in 30.4% of runs on one benchmark. Instructions not to cheat left rates high on one task. Limit: tasks with a visible scorer, mostly one model.
- **S152. Anthropic, [Claude 3.7 Sonnet System Card](https://assets.anthropic.com/m/785e231869ea8b3b/original/claude-3-7-sonnet-system-card.pdf) (February 2025) and [System Card: Claude Opus 4 & Claude Sonnet 4](https://www-cdn.anthropic.com/4263b940cabb546aa0e3283f35b686f4f3b2ff47.pdf) (May 2025), section 6.** Practice (vendor reports). Section 6 read. The model sometimes special-cases tests after repeated failures and sometimes edits tests. Advises monitoring for unexpected edits to test files. Later models hard-coded less, but impossible-task hack rates without an anti-hacking prompt stayed at 45% to 47%. Limit: vendor self-report, internal evaluations.
- **S153. Simon Willison (2025), [Your job is to deliver code you have proven to work](https://simonwillison.net/2025/Dec/18/code-proven-to-work/), 18 December 2025.** Opinion. Full text read. Asks for evidence of a manual test in the pull request and an automated test that fails if the change is reverted.

### Error handling

- **S154. Ding Yuan, Yu Luo, Xin Zhuang, Guilherme Renna Rodrigues, Xu Zhao, Yongle Zhang, Pranay U. Jain and Michael Stumm (2014), [Simple Testing Can Prevent Most Critical Failures: An Analysis of Production Failures in Distributed Data-Intensive Systems](https://www.usenix.org/conference/osdi14/technical-sessions/presentation/yuan), OSDI 2014.** Research (198 sampled failures, 48 catastrophic, five systems). Full text read. 92% of catastrophic failures came from incorrect handling of explicitly signalled non-fatal errors. 35% came from three trivial patterns. 58% could have been caught by simple tests of the error-handling code. Limit: human-written systems, before LLMs.
- **S155. Mohammed Latif Siddiq, Shafayat H. Majumder, Maisha R. Mim, Sourov Jajodia and Joanna C. S. Santos (2022), [An Empirical Study of Code Smells in Transformer-based Code Generation Techniques](https://doi.org/10.1109/SCAM55253.2022.00014), SCAM 2022, 71–82. DOI 10.1109/SCAM55253.2022.00014.** Research. Full text read. Training sets contain `try`/`except`/`pass` patterns, and a fine-tuned model reproduced them. Limit: a very small model and 2022 Copilot. Thin evidence for current agents.

### Descriptions

- **S156. Jingzhi Gong, Giovanni Pinna, Yixin Bian and Jie M. Zhang (2026), [Analyzing Message-Code Inconsistency in AI Coding Agent-Authored Pull Requests](https://doi.org/10.1145/3793302.3793583), MSR 2026, 827–831. DOI 10.1145/3793302.3793583. [arXiv 2601.04886](https://arxiv.org/abs/2601.04886).** Research (short paper, 23,247 agent pull requests). Full text read. 1.7% showed high inconsistency between description and code. Descriptions claiming unimplemented changes were the most common type (45.4%). These pull requests were accepted 28.3% of the time, against 80.0%, and took 3.5 times longer to merge. Limit: a heuristic inconsistency score, association only.
- **S157. Tao Xiao, Hideaki Hata, Christoph Treude and Kenichi Matsumoto (2024), [Generative AI for Pull Request Descriptions: Adoption, Impact, and Developer Interventions](https://doi.org/10.1145/3643773), Proc. ACM Softw. Eng. 1(FSE), 1043–1065. DOI 10.1145/3643773.** Research (18,256 pull requests). Full text read. Generated descriptions were associated with faster review. Where developers edited them, deletion was the most common edit (22.9%), and they added intent and testing details. Limit: a 2023 tool, observational.
- **S158. Simon Willison (2026), [Hide your slop PR descriptions behind <details><summary>](https://simonwillison.net/2026/Nov/9/details-summary/), 9 November 2026.** Opinion. Full text read. Puts a short human-written opener first and folds the agent's long description into a collapsed block. Notes that the agent's text is usually accurate but too long.

### Policies and practitioner guidance

- **S159. LLVM, [AI Tool Use Policy](https://llvm.org/docs/AIToolPolicy.html).** Practice (project policy, checked 9 November 2026). Full text read. A human must read and review all generated code or text before asking for review, and must be able to answer questions about it. Strongly recommends writing pull request descriptions yourself. Defines an "extractive" contribution as one whose review cost exceeds its benefit.
- **S160. Python Developer's Guide, [Guidelines for using AI tools](https://devguide.python.org/getting-started/ai-tools/).** Practice (project policy, checked 9 November 2026). Full text read. Asks whether the change is necessary, for minimal and focused changes that follow existing patterns, and for explanations in the contributor's own words. Forbids altering or bypassing tests to make them pass.
- **S161. Linux kernel, [Kernel guidelines for tool-generated content](https://docs.kernel.org/process/generated-content.html) and [AI coding assistants](https://docs.kernel.org/process/coding-assistants.html).** Practice (project documentation, master checked 9 November 2026). Full text read. Submitters must understand the whole submission and respond to review. They should disclose tool use and say what they could not build, test or reproduce. AI agents must not add `Signed-off-by`.
- **S162. Ghostty, [AI Usage Policy](https://github.com/ghostty-org/ghostty/blob/main/AI_POLICY.md).** Practice (project policy, checked 9 November 2026). Full text read. Requires disclosure and that contributors can explain all code without AI. Asks that AI-written text be edited by a human because it is overly verbose.
- **S163. curl, [Contribute: On AI use in curl](https://curl.se/dev/contribute.html), and Daniel Stenberg (2025), [Death by a thousand slops](https://daniel.haxx.se/blog/2025/07/14/death-by-a-thousand-slops/), 14 July 2025.** Practice and opinion (project policy and maintainer report, checked 9 November 2026). Full text read. AI-assisted pull requests must meet all normal requirements. AI-written reports are "too wordy and rarely to the point". Each security report takes several team members' time to assess.
- **S164. Simon Willison (2025), [Not all AI-assisted programming is vibe coding (but vibe coding rocks)](https://simonwillison.net/2025/Mar/19/vibe-coding/), 19 March 2025.** Opinion. Full text read. His rule is not to commit code he could not explain to someone else.

### Evidence not carried forward

- GitClear's 2024 report covers the same series to 2023 and is superseded by S116. Its 2024 row was a projection.
- Liu et al., "Refining ChatGPT-Generated Code" (TOSEM 2024, DOI 10.1145/3643674), is sometimes cited for poor error handling. It does not study exception handling, so we do not cite it for that.
- We found no study measuring how often reviewers miss duplicated helpers, how often agents falsely report passing tests in real repositories, or how often current agents swallow errors. We found no study testing whether search-before-write instructions reduce duplication.
